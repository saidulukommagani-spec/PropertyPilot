# PropertyPilot Business Flow Audit

**Audit basis:** Business context, enterprise checklist, roadmap, and implementation under `propertypilot-backend`, `propertypilot-frontend`, `mobile_app`, plus repository migration/configuration roots. The operational backend is the Spring Boot project (`propertypilot-backend`); `backend/`, `database/`, `admin-portal/`, and `infrastructure/` are empty placeholders. This audit is a source inspection, not a runtime or security penetration test.

## End-to-end flows

| Flow | Current implementation and evidence | Finding |
|---|---|---|
| Customer onboarding | `AuthController`/`AuthServiceImpl`, `UserController`, `CustomerVerification*`, customer profile/address/preferences APIs; users and customers are separate persisted concepts. Public `POST /api/v1/users` exists in `SecurityConfig`. | Foundation exists, but public user creation does not establish customer ownership/roles safely by itself; external lead-to-customer conversion is not demonstrated as an atomic audited flow. HIGH. |
| Property management | `PropertyController`, `PropertyServiceImpl`, `PropertyOwnerController` and owner service; `Property` plus `PropertyOwnerEntity`, `PropertyDocumentEntity`, `PropertyLocationEntity`. | Multi-owner and document links exist. Confirm service requests validate that supplied customer owns/is authorized for the supplied property; IDs are accepted from request. MEDIUM/HIGH authorization gap. |
| Property health check | No named health-check workflow/service/domain entity/API was found. Generic service catalog + request can represent inspections and document checks. | No composed physical/document health assessment, checklist/result aggregation, or report lifecycle proven. Business functionality gap HIGH; can likely reuse catalog, service request, evidence, report, and document structures. |
| Lead management | `LeadController`, `LeadServiceImpl`, `LeadActivityServiceImpl`, lead repositories/entities; sources and assignment/activity structures are present. | Basic capture and management exist. Verify conversion to customer/deal and lead data deduplication; `LeadJpaRepository`/`LeadRepository` and `CustomerJpaRepository`/`CustomerRepository` are duplicate repository abstractions. MEDIUM. |
| Deal management | `DealController`, `DealServiceImpl`, `DealBillingServiceImpl`; deal participants, milestones, activities, service request links. | Deal workflow foundation and links exist. Audit exact transaction boundaries/transition coverage before relying on completion-to-service/billing. MEDIUM. |
| Subscription | Plan, version, entitlement, consumption, renewal, add-on, pause, lifecycle and notification classes; three schedulers. | Broad foundation, but `SubscriptionAutoRenewScheduler` creates a SUCCESS renewal and new subscription without charging a payment provider; no idempotency/locking visible in scheduler. Critical billing correctness gap. Carry-forward/consumption semantics require confirmation. |
| Pricing and estimates | Pricing profile/parameter tables; `PricingCalculatorServiceImpl` and rule engine; estimate/quote/discount entities, rules, approvals, history. | Engine calculates vendor + travel + DA + overhead + margin + GST, but cluster/ETA discounts are hard-coded zero; coupon/subscription discount is not applied in this calculation. Estimate storage/snapshot and quote-line items are not shown as part of calculation. Roadmap active priority remains incomplete. HIGH. |
| Service request | `ServiceRequestController`, `ServiceRequestServiceImpl`, workflow/status-history, eligibility and billing dependencies. | Status path, assignment and completion hooks exist. Controller request bodies lack `@Valid`; lookup/update endpoints have no object ownership checks. Create accepts request amount instead of enforcing quote snapshot. Critical authorization, HIGH pricing integrity. |
| Agent assignment | `AgentAssignmentServiceImpl`; agent, skill, assignment entities/repositories; assignment operations also live in `ServiceRequestServiceImpl`. | Duplicate ownership: assignment service explicitly throws/defer lifecycle while request service performs assignment. Agent eligibility/race safety and retries need review. Assignment endpoints use caller-supplied actor IDs. HIGH. |
| Visit | `VisitServiceImpl`, `VisitController`; visits linked to assignments, one visit per assignment check. | Scheduled/start/complete/cancel lifecycle exists. `maxVisitsAllowed` and `visitMandatory` are not enforced; one-visit-per-assignment conflicts with multiple visits unless multiple assignments are created. Business gap HIGH. |
| Evidence | `EvidenceServiceImpl`, `EvidenceController`, evidence type/repository, GPS verification. | Service-configured before/after/signature/document/GPS completion checks exist. Evidence service prevents duplicate type per visit, but stores a supplied `fileUrl` and checksum; no upload ownership, immutable object storage, content inspection, or evidence-to-visit authorization demonstrated. Validation checks “exists”, not quality/approval. HIGH production gap. |
| Completion | `CompletionValidationServiceImpl`; `ServiceRequestServiceImpl` invokes it. | Visit is optional when `requiresVisit=false`; required evidence/GPS checks are configuration driven. `visitMandatory` is unused. Evidence checks aggregate across any visit rather than enforce per visit/quantity; completion rules lack document/video validation beyond document type. MEDIUM/HIGH. |
| Billing | `BillingServiceImpl`, `DealBillingServiceImpl`, invoice entities/repositories/controllers. | Basic invoice creation/listing. Tax is always zero, currency fixed INR, invoice number is millisecond-based, no visible line items/tax jurisdiction/credit-note lifecycle. `getAllInvoices` unpaged. HIGH production/billing compliance gap. |
| Payment | `PaymentServiceImpl`, `PaymentController`, payment/refund schema. | `recordPayment` trusts caller request, marks SUCCESS immediately, generates random idempotency key, then marks invoice PAID; no gateway capture/webhook/signature/reconciliation. Customer role can query arbitrary payment/invoice IDs. Critical. |
| Notifications | notification/template/subscription notification services and scheduler; notification entities. | In-app persistence/reminder foundation exists. Delivery channel provider/retry/dead-letter and user preference/consent behavior not established. MEDIUM production gap. |
| Admin operations | Many admin controllers/dashboard/report/pricing/subscription endpoints; `SecurityConfig` plus `@PreAuthorize`. | Mixed `hasRole`/`hasAuthority` semantics and URL/controller route prefixes diverge (`/api/v1/...` security matchers vs several `/api/...` mappings); method-level protection is inconsistent. Admin capabilities exist but access policy is unreliable without integration verification. CRITICAL. |

## Cross-cutting business conclusions

- Product model remains service-centered in the core flow, but legacy marketplace/vendor/partner entities and `/marketplace-listings` security route remain. They conflict with the stated customer-facing “PropertyPilot owns the relationship” principle unless kept strictly internal and unused.
- Configurable visit/evidence fields are on `ServiceEntity`; completion uses several. `visitMandatory` and `maxVisitsAllowed` appear unconsumed. Service catalog administration/configuration is not established in reviewed controller inventory.
- The schema/model is much broader than active service layer: complaint, marketplace, partner/vendor, monitoring, NRI relationship, offline sync, refund, and rating domains have persistence classes/repositories, but corresponding end-to-end APIs/service implementations are missing or incomplete in the listed service catalog.
- Roadmap claim of 97–99% business functionality is not supported by pricing discount omissions, health-check composition gap, renewal without payment, and incomplete customer/provider operational boundaries.
